# 答辩要点（二手车检测报告与车况可信存证平台）

> 用法：前半部分用于开场陈述和 PPT 讲解，后半部分是问答弹药。
> 原则：先讲人话，再讲实现；不夸大“区块链”，主动说清边界，反而更容易拿分。

---

## 一、开场陈述（背熟一版即可）

### 30 秒版

> 这是一个二手车检测报告平台。它除了把检测流程管起来，更重要的是让每份报告“出门即带指纹”：报告关键内容固化成结构化数据，出具时计算 SHA-256 指纹并串成哈希链。之后任何人改动数据，公开验真页都能发现，并指出改的是哪个字段。系统覆盖检测师、车商、买家、平台运营、仲裁员五类角色，从建档、检测、复核、出证、验真，一直做到交易意向和纠纷举证。

### 1 分钟版（在 30 秒版后补三句）

> 第一，报告指纹算的是结构化 JSON，不是 PDF。因为 PDF 每次导出字节都可能不同，哈希会变；JSON 只要内容一样，哈希永远一样。
> 第二，指纹不是一条条孤立的，而是首尾相连成链，改任何一条都会导致后面全部断裂，验真时能定位到具体记录。
> 第三，业务流程是闭环的：检测单有状态机，出证要复核，同车同周期只能有一份有效报告，报告更正会生成新版本并重新存证，旧版本保留可查。

## 二、项目与题库要求的对应关系

| 题库要求 | 我们的实现 |
| --- | --- |
| 五类业务角色（另有管理员）与权限 | JWT 登录 + 角色注解 + 数据范围过滤，前端菜单按角色显示 |
| 车辆档案、检测模板、检测单 | 17 张表中的车辆/模板/模板项/检测单/检测项 |
| 检测单状态流转与撤回 | 待检测→检测中→待出报告→待复核→已出报告，撤回留原因并写审计 |
| 规则校验（缺项、评分范围、缺陷等级） | 提交前缺项统计；评分 0–100、缺陷 0–3 校验 |
| 报告生成、复核、生效 | 评分引擎算分定价，生成草稿并建审批任务，复核通过才生效 |
| 报告版本与更正 | 更正走独立审批，通过后生成 v2、重新存证，v1 归档为 SUPERSEDED |
| 同车同周期唯一有效报告 | Redis 车辆级锁 + 90 天有效期查询（可配置） |
| 哈希链存证与验真 | 规范化 JSON → SHA-256 → 链式记录；公开验真 + 字段级差异 |
| 验真留痕 | 每次验真写 `verify_record`，含结果、IP、差异字段 |
| 交易意向（出价/还价/成交） | 意向单状态机 PENDING→COUNTERED→ACCEPTED/REJECTED/CANCELLED |
| 纠纷举证与仲裁 | 案件 + 材料包，自动纳入报告与链记录，支持受理/补充/裁决/撤诉 |
| 统计与导出 | 区间统计看板 + 服务端 POI 生成 Excel + 导出审计 |
| 审计补偿 | `audit_log` 记录关键动作，登录也留痕，支持分页查询 |

## 三、系统结构（口述版架构图）

```
浏览器（Vue 3 + Vite + Element Plus）
        │  HTTP / JSON（JWT）
        ▼
Spring Boot 3.3.5（Java 21）
  Controller → Service → Mapper（MyBatis-Plus）
  ├─ 认证与权限：JWT 拦截器 + @RequireRole + 数据范围
  ├─ 业务域：车辆 / 检测 / 报告 / 审批 / 意向 / 纠纷
  ├─ 存证域：规范化器 + 哈希链 + 验真 + 验真留痕
  ├─ 统计审计：JdbcTemplate 聚合 + POI 导出 + audit_log
  └─ 附件：线程池异步处理 + MinIO
        │
        ├─ MySQL 8（17 张业务表，Flyway 管理版本）
        ├─ Redis 7（车辆级分布式锁）
        └─ MinIO（检测照片对象存储）
```

数据模型按四组记忆：

1. 组织与档案：`sys_user`、`vehicle`、`maintenance_record`
2. 检测与报告：`inspection_template`、`inspection_template_item`、`inspection_order`、`inspection_item`、`inspection_report`、`approval_task`、`attachment`
3. 存证与验真：`evidence_chain`、`chain_head`、`verify_record`
4. 交易与治理：`intention_order`、`dispute_case`、`dispute_evidence`、`audit_log`

## 四、核心机制问答

### A. 存证与验真（最容易被追问，优先准备）

**Q1：为什么不用区块链？**
> 我们解决的是“报告有没有被改、谁在什么时候出的证”，不是多方共同记账。单平台场景下，哈希链 + 只追加表已经能提供防篡改和可追溯，成本和复杂度都低。
> 如果将来需要第三方公信，把链头定期锚定到外部时间戳服务或联盟链即可，架构不用重写。我们不会把它说成“区块链”，避免被问共识、节点、51% 攻击这些并不适用的点。

**Q2：为什么哈希的是 JSON，不是 PDF？**
> PDF 受字体、导出时间影响，同一份报告每次生成字节都可能不同，哈希会变。我们把报告关键字段固化成字段顺序固定的 JSON 快照，内容一样哈希就永远一样。报告页面怎么排版都可以变，底层快照不变。

**Q3：规范化具体做了什么？**
> 六条规则：字段顺序写死；UTF-8 且字符串做 NFC 归一化和去首尾空格；空值统一（字符串空串、数值 0）；金额统一用“分”的整数；时间统一 UTC 且截断到秒；缺陷列表按编码、等级、扣分排序，避免录入顺序影响哈希。

**Q4：哈希链的公式是什么？**
> `report_hash = SHA-256(规范化 JSON)`；`record_hash = SHA-256(prev_hash + report_hash + issued_at)`；第一条的 `prev_hash` 是 64 个 0。每条记录都依赖前一条，改一条后面全断。

**Q5：并发出证时怎么保证链不断裂？**
> `chain_head` 表只存一行（当前序号和最后一个哈希）。追加记录时先 `SELECT ... FOR UPDATE` 锁住这一行，事务提交才释放，所以序号一定连续、前序哈希一定接得上。表上还有序号和报告 ID 的唯一约束兜底。

**Q6：验真怎么知道哪个字段被改了？**
> 验真时用数据库当前数据重新生成快照、重算哈希，和链上的 `report_hash` 比。不一致时，把存证当时的规范化 JSON 和当前 JSON 逐字段比较，输出字段名、存证值、当前值。同时校验整条链的序号和前后指针。每次验真都会写一条 `verify_record`。

**Q7：报告更正为什么不直接改原报告？**
> 已生效报告是已经对外承诺过的凭证，不能原地改。更正走独立审批任务，审批通过后重新评分、重新出证，生成新编号的 v2 并写第二条链记录，v1 置为 SUPERSEDED 但保留可验真。这样历史可追溯，也不会出现“同一份报告两个内容”。

**Q8：附件为什么没有纳入报告哈希？**
> 报告快照覆盖的是结构化结论字段（车架号、里程、分数、等级、缺陷、估价、出具时间）。附件原图单独存 SHA-256 指纹，防止图片被替换。如果要把照片也纳入存证，可以把附件指纹列表加入快照，这是明确的扩展点。

**Q9：如果数据库管理员把整条链都改了怎么办？**
> 这是中心化存证的边界，我们不宣称“绝对不可篡改”。当前能做到的是：改任何数据都会和链上的指纹对不上，验真会失败并留痕。生产环境可以再加三层：链头定期外锚定、数据库操作审计、对象存储 WORM/备份。答辩时主动说清边界，比硬说“不可篡改”更稳。

### B. 评分与估价

**Q10：评分怎么算？**
> 六个大类固定权重：外观 15、内饰 10、发动机 25、底盘 20、事故 20、水泡火烧 10。每类内部按检测项权重加权平均，再按大类权重汇总成总分。评分引擎是纯函数，不依赖数据库，方便单测。
> 等级：90 分及以上 S，80 及以上 A，70 及以上 B，60 及以上 C，其余 D。缺陷等级对应扣分：无 0、轻微 3、一般 6、严重 10。

**Q11：估价怎么来的？**
> 以 12 万为基准乘以得分率得到中位价，上下浮动 8% 得到区间，金额按分存储、取整到 10 元。它是平台参考价，不替代专业评估，这一点要说清楚。

### C. 业务规则与并发

**Q12：同车同周期唯一怎么保证？**
> 出证前按车辆加 Redis 锁，锁内查询该车 90 天内是否已有 ACTIVE 报告，有就拦截。90 天是配置项 `app.rules.report-valid-days`，可以调。数据库唯一约束主要保证报告编号、单据版本、链序号这些硬唯一项。

**Q13：重复提交怎么处理？**
> 报告生成会校验检测单状态和是否已有报告；意向单、纠纷单会校验同一用户是否有进行中的记录；审批任务有 PENDING→APPROVED/REJECTED 状态机，处理过就不能再处理；编号冲突用唯一约束 + 重试。关键出证动作还有 Redis 锁。

**Q14：为什么不用工作流引擎？**
> 当前只有报告复核和更正复核两类审批节点，用 `approval_task` 表加状态机足够，部署和讲解都简单。如果节点变多、要可视化流程设计，再换 Flowable 这类引擎更合适。

**Q15：为什么是单体，不做微服务？**
> 课程项目规模下，单体部署简单、事务好保证、演示稳定。业务域已经按包拆开，未来真要拆服务，边界是现成的。

**Q16：Redis 挂了会怎样？**
> 车辆级锁失效，极端并发下同一辆车可能同时通过“90 天内无生效报告”的查询。当前主要靠应用层查询和数据库事务兜底，单机演示场景风险很低。生产环境会更严谨：锁降级策略、单独的出证约束表或数据库悲观锁。这一点如实回答即可。

### D. 权限与安全

**Q17：权限是怎么控制的？**
> 登录发 JWT，里面带用户 ID、用户名、角色，有效期 12 小时。拦截器解析后放进请求上下文，方法和类上的 `@RequireRole` 控制角色，Service 层再做数据范围过滤：检测师只能看自己被指派的检测单，买家只能看自己的意向和纠纷，车商响应意向时会校验车辆归属。前端路由守卫只是体验，真正拦截在后端。

**Q18：密码怎么存的？**
> BCrypt 加密存储，不存明文。演示账号统一密码是 123456，生产会强制改密并加登录失败锁定。

**Q19：审计能查到什么？**
> 关键动作都会写 `audit_log`：创建、开始、提交、撤回、出证、复核、更正、导出、纠纷、登录等。记录操作人、角色、业务类型、业务 ID、详情、IP 和时间。检测单详情里的流转时间线就是按单据聚合审计记录得到的。验真记录还会保存字段差异，页面上可展开查看存证值与当前值。

### E. 工程实现

**Q20：附件上传为什么要异步？**
> 现场一次传几十张手机原图，如果同步压缩会拖慢提交接口。我们先把文件落库、存 MinIO，再用 4 到 8 个线程、200 容量的队列异步压缩、生成缩略图、计算原图指纹；队列满时降级为同步执行，避免丢任务。前端轮询处理状态。

**Q21：时间精度踩过什么坑？**
> MySQL 的 DATETIME 默认秒精度，如果传入带毫秒的时间会被四舍五入，导致入库值和参与哈希的值差一秒，验真就必然失败。修复方式是在出证前把时间截断到秒，入库和哈希使用同一个值。这是实际调试出来的，不是设计时就想到的。

**Q22：测试做了什么？**
> 15 个单元测试，重点覆盖三块最容易出错的逻辑：规范化（同内容必须同哈希、空值/排序稳定）、哈希链（正常链、断裂链、篡改记录）、评分引擎（权重、等级边界）。业务链路做接口和页面实测，从建档走到验真、意向、纠纷、统计。

**Q23：代码规模？**
> 后端 Java 约 4600 行、前端约 3800 行、SQL 迁移约 300 行，17 张业务表、13 个页面、40 多个接口。规模是为了完整闭环，不是为了堆量。

## 五、高频追问快答

| 追问 | 一句话回答 |
| --- | --- |
| 哈希会不会碰撞？ | SHA-256，工程上可忽略；真担心可换 SHA-512 或加盐。 |
| 为什么要排序缺陷列表？ | 录入顺序不应影响指纹，否则同一份报告会有多个合法哈希。 |
| 时间为什么用 UTC？ | 避免服务器时区变化导致历史报告验真失败。 |
| 报告没生效能验真吗？ | 不能，只接受 ACTIVE/SUPERSEDED，草稿会明确提示。 |
| 二维码里是什么？ | 公开验真页地址，带报告编号，无需登录。 |
| 为什么报告编号带随机数？ | 同一天出证量大时避免顺序号被猜；唯一约束 + 冲突重试保证不重复。 |
| 撤回检测单有什么限制？ | 已出报告、已撤回不能再撤；要校验操作人身份。 |
| 评分能改吗？ | 生效报告不能改；更正要重新审批并出新版本。 |
| 统计导出是真 Excel 吗？ | 是，服务端用 POI 生成 xlsx，包含汇总和检测单明细。 |
| 前端为什么用 Element Plus？ | 表格、表单、弹窗组件完整，能把精力放在业务和存证上。 |

## 六、项目不足与改进方向（主动讲，显得清醒）

1. **服务端 PDF 未做**：当前报告用浏览器打印为 PDF；统计导出是服务端 Excel。若要做正式报告 PDF，可用模板引擎 + 字体嵌入生成。
2. **存证是中心化单库**：可通过链头外锚定、对象存储 WORM、第三方时间戳提升公信力。
3. **异步是进程内线程池**：重启会丢未处理任务，生产可换消息队列并做重试与死信。
4. **附件未纳入报告哈希**：可把附件指纹列表加入快照，扩大验真覆盖面。
5. **缺少自动化集成测试**：目前单测覆盖核心算法，业务链路靠手工实测，后续可补 Testcontainers。
6. **权限是角色级 + 简单数据范围**：更复杂场景可引入细粒度数据权限或组织架构。

> 回答技巧：先说“目前做到哪”，再说“为什么这样取舍”，最后说“下一步怎么做”。不要等评委问出来才承认。

## 七、现场答辩策略

1. **先结论后细节**：每个问题先给一句话结论，再展开两点，不要一上来讲代码。
2. **不吹“区块链”**：说“哈希链 + 只追加 + 可信存证”，被问区块链时按 Q1 回答。
3. **主动暴露一个真实坑**：DATETIME 秒精度那个问题很好用，能证明是真做过，不是纸上设计。
4. **演示失败不慌**：直接切录屏，说明“现场环境问题，核心逻辑看录屏”，继续讲原理。
5. **被问住时**：承认“这块目前没做/没深入”，给出改进思路，不要编。
6. **时间控制**：陈述控制在 6 分钟内，留至少 4 分钟给演示和提问。

## 八、如果被问到分工

可以这样回答：按业务纵向分工，而不是按页面分工——

- 检测与报告线：车辆档案、检测单状态机、录入、评分、报告版本与更正
- 存证与验真线：规范化、哈希链、审批出证、公开验真、字段差异
- 交易与治理线：意向单、纠纷举证、统计导出、审计日志

这样每条线都能独立演示、独立讲解，代码边界也清楚。
